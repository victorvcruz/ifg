\section{Justificativa de Negócio}

O mercado de aluguel de quadras esportivas no Brasil é fragmentado e predominantemente analógico. A maioria dos estabelecimentos ainda opera por meio de ligações telefônicas ou mensagens de WhatsApp para gerenciar reservas, o que gera ineficiências como dupla reserva, horários ociosos não preenchidos e dificuldade de escalabilidade. O cliente final, por sua vez, enfrenta dificuldade para encontrar quadras disponíveis, comparar preços e confirmar reservas de forma rápida.

A QuadraLivre surge como uma plataforma digital que automatiza todo o ciclo de reserva: o usuário busca quadras por localização e modalidade, visualiza a grade de horários em tempo real e confirma a reserva instantaneamente; o dono da quadra gerencia preços, horários e bloqueios por meio de um painel web. O projeto se justifica pelo potencial de redução do tempo ocioso das quadras em até 30\%, aumento do faturamento dos estabelecimentos e melhoria significativa da experiência do usuário final, que elimina intermediários manuais.

\section{Objetivos do Projeto}

\begin{itemize}
    \item Desenvolver um aplicativo mobile para que usuários encontrem e reservem quadras esportivas em tempo real.
    \item Desenvolver um painel web para que administradores gerenciem seus estabelecimentos, quadras, preços e horários.
    \item Implementar um sistema de reservas com confirmação imediata e controle de concorrência para evitar duplicidade.
    \item Entregar o MVP em até 4 meses com as funcionalidades essenciais de busca, reserva e gestão.
\end{itemize}

\section{Análise de Viabilidade Econômica}

\subsection{Premissas Adotadas}

\begin{itemize}
    \item Custo total do projeto (investimento inicial): R\$ 63.800,00
    \item Custo operacional mensal estimado (servidores, manutenção, suporte): R\$ 2.500,00
    \item Modelo de receita: assinatura mensal de R\$ 97,00 por estabelecimento + taxa de 10\% sobre o valor de cada reserva
    \item Número de estabelecimentos captados no primeiro ano: 15
    \item Média de reservas por estabelecimento por mês: 80
    \item Valor médio por reserva: R\$ 100,00
    \item Horizonte de análise: 12 meses
\end{itemize}

\subsection{Cálculo do Retorno sobre o Investimento (ROI)}

\begin{equation}
ROI = \frac{\text{Receita Líquida Anual} - \text{Investimento Inicial}}{\text{Investimento Inicial}} \times 100
\end{equation}

Receita Líquida Anual = Receita Anual Bruta $-$ Custos Operacionais Anuais:

$$\text{Receita Líquida Anual} = R\$ \; 161.460{,}00 - (R\$ \; 2.500{,}00 \times 12) = R\$ \; 131.460{,}00$$

$$ROI = \frac{R\$ \; 131.460{,}00 - R\$ \; 63.800{,}00}{R\$ \; 63.800{,}00} \times 100 = \frac{R\$ \; 67.660{,}00}{R\$ \; 63.800{,}00} \times 100$$

$$\boxed{ROI = 106{,}05\%}$$

\subsection{Cálculo do Payback Simples}

\begin{equation}
\text{Payback Simples} = \frac{\text{Investimento Inicial}}{\text{Receita Líquida Mensal}}
\end{equation}

Receita Líquida Mensal = R\$ 13.455,00 $-$ R\$ 2.500,00 = \textbf{R\$ 10.955,00}

$$\text{Payback Simples} = \frac{R\$ \; 63.800{,}00}{R\$ \; 10.955{,}00}$$

$$\boxed{\text{Payback Simples} = 5{,}82 \text{ meses}}$$

\subsection{Conclusão da Viabilidade}

O projeto apresenta um ROI de 106,05\% no primeiro ano, indicando que o capital investido mais que dobra ao final do horizonte de análise. O Payback Simples de aproximadamente 6 meses demonstra que o investimento inicial é recuperado em meio período de operação, o que é considerado bastante favorável para projetos de software. Diante dos indicadores, o projeto é economicamente viável e recomenda-se sua execução.

\chapter{Declaração do Escopo do Projeto}

\section{Descrição do Projeto}

O projeto QuadraLivre consiste no desenvolvimento de uma plataforma digital para reserva de quadras esportivas, composta por um aplicativo mobile voltado para usuários jogadores e um painel web voltado para administradores de estabelecimentos. O objetivo é automatizar o processo de reserva, eliminando a dependência de canais manuais como telefone e WhatsApp, e oferecendo uma grade de horários em tempo real, confirmação imediata de reservas e ferramentas de gestão para os donos das quadras.

\section{Descrição do Produto}

O produto é composto por dois módulos principais:

\subsection{Módulo Usuário (Aplicativo Mobile)}
\begin{itemize}
    \item Cadastro e autenticação de conta (email e senha).
    \item Busca de quadras por localização geográfica e modalidade esportiva (futebol, beach tennis, vôlei, tênis, etc.).
    \item Visualização da grade de horários disponíveis em tempo real para cada quadra.
    \item Seleção de horário e confirmação imediata da reserva.
    \item Histórico de reservas realizadas.
    \item Notificação de lembrete de reserva.
\end{itemize}

\subsection{Módulo Administrador (Painel Web)}
\begin{itemize}
    \item Cadastro do estabelecimento (endereço, fotos, descrição, modalidades oferecidas).
    \item Cadastro e gerenciamento de quadras (nome, tipo de superfície, capacidade).
    \item Configuração de preços diferenciados por horário e dia da semana.
    \item Visualização e gerenciamento da grade de reservas.
    \item Bloqueio manual de horários para manutenção ou uso próprio.
    \item Relatório básico de reservas e faturamento.
\end{itemize}

\section{Inclusões do Escopo}

\begin{itemize}
    \item Cadastro e autenticação de usuários (jogadores e administradores).
    \item Busca de quadras por localização e modalidade esportiva.
    \item Grade de horários disponíveis em tempo real.
    \item Reserva de horário com confirmação imediata e controle de concorrência.
    \item Painel administrativo web para gestão de estabelecimento, quadras, preços e horários.
    \item Bloqueio manual de horários pelo administrador.
    \item Notificação de lembrete de reserva para o usuário.
    \item Histórico de reservas para o usuário.
    \item Relatório básico de reservas para o administrador.
\end{itemize}

\section{Exclusões do Escopo}

\begin{itemize}
    \item \textbf{Divisão de checkout (rache):} o sistema não fará o rateio automático do valor da reserva entre os participantes. O pagamento da reserva é integral por parte de quem realiza o agendamento.
    \item \textbf{Sistema de matchmaking:} não será criada funcionalidade para formação de partidas públicas com desconhecidos para preencher vagas.
    \item \textbf{Gateway de pagamento integrado:} nesta versão, a confirmação da reserva é feita sem processamento financeiro online. O pagamento será tratado presencialmente ou por acordos prévios entre as partes.
    \item \textbf{Marketplace de produtos esportivos:} não haverá venda de produtos ou equipamentos dentro da plataforma.
    \item \textbf{Aplicativo para administradores:} o módulo de administração será exclusivamente web, sem versão mobile dedicada para gestão.
    \item \textbf{Chat interno entre usuários:} não haverá mensageria direta entre jogadores ou entre jogador e estabelecimento.
    \item \textbf{Multi-idioma:} a plataforma será entregue exclusivamente em português brasileiro.
\end{itemize}

\section{Restrições do Projeto}

\begin{itemize}
    \item Prazo máximo de 16 semanas para entrega do MVP.
    \item Equipe fixa de 4 pessoas (não é possível contratação adicional).
    \item Orçamento máximo de R\$ 65.000,00.
    \item A plataforma deve funcionar em dispositivos Android 8.0+ e iOS 14+.
\end{itemize}

\section{Premissas do Projeto}

\begin{itemize}
    \item A equipe terá acesso às ferramentas de desenvolvimento necessárias (IDEs, servidores de teste, Figma).
    \item Os dados de quadras e estabelecimentos serão fornecidos pelos próprios donos no momento do cadastro.
    \item A infraestrutura em nuvem será dimensionada para suportar até 100 requisições simultâneas.
    \item O protótipo Figma será aprovado pelo cliente antes do início do desenvolvimento.
\end{itemize}

\section{Ajuste para 16 Semanas (Estratégia de Compressão)}

O cronograma teórico resulta em 93,0 dias ($\approx$18,6 semanas), excedendo o limite de 16 semanas (80 dias úteis) em \textbf{13 dias}. As seguintes estratégias de compressão serão aplicadas:

\subsection{\textit{Fast-tracking} (Paralelismo Ampliado)}
\begin{itemize}
    \item Iniciar V (Cadastro Estabelecimento Web) parcialmente em paralelo com P (API Administração), utilizando \textit{mocks} das APIs durante o desenvolvimento do frontend. Redução estimada: \textbf{4 dias}.
    \item Iniciar X (Grade Reservas/Bloqueios Web) antes da conclusão total de W, trabalhando nos componentes de visualização enquanto a lógica de preços é finalizada. Redução estimada: \textbf{3 dias}.
\end{itemize}

\subsection{\textit{Crashing} (Alocação de Recurso Adicional)}
\begin{itemize}
    \item Alocar desenvolvedor mobile como suporte no pacote X (Grade Reservas/Bloqueios Web), atividade mais longa do caminho crítico no frontend web (7,3 dias $\rightarrow$ estimativa reduzida para 5 dias). Redução: \textbf{2,3 dias}.
\end{itemize}

\subsection{Redução de Escopo Interno}
\begin{itemize}
    \item Simplificar Y (Relatórios Web): entregar apenas relatório de reservas na v1, postergando relatório de faturamento para iteração seguinte. Redução: \textbf{2 dias} (de 4,0 para 2,0 dias).
\end{itemize}

\subsection{Paralelismo Backend-Frontend}
\begin{itemize}
    \item As equipes de backend e frontend mobile/web trabalham simultaneamente a partir da aprovação do protótipo (I), com o backend priorizando a API de Administração (P) sobre a API de Busca (N) para destravar o caminho crítico mais cedo.
\end{itemize}

\textbf{Resultado após compressão:} Redução total estimada de $\approx$11,3 dias + margem de 1,7 dias absorvida pela folga do caminho quase-crítico (N$\rightarrow$O$\rightarrow$S$\rightarrow$T). Duração efetiva: \textbf{$\approx$80 dias úteis}, compatível com 16 semanas.

\section{Conclusão do Cronograma}

O caminho crítico do projeto QuadraLivre está concentrado no desenvolvimento do painel web administrativo (P, V, W, X e Y), que depende da API de Administração e acumula a maior duração total. Este é o gargalo do projeto e deve receber atenção prioritária. Qualquer atraso nas atividades do caminho crítico impacta diretamente a data de entrega final.

O caminho quase-crítico (N $\rightarrow$ O $\rightarrow$ S $\rightarrow$ T, folga de 1,6 dias) exige monitoramento constante, pois qualquer desvio superior a 1,6 dias transforma a trilha mobile no novo caminho crítico.

As atividades com folga significativa (Q, R, U, Z) oferecem margem para realocação de recursos e absorção de desvios sem comprometer o prazo.
